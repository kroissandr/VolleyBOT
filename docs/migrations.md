# Миграции PostgreSQL

Каждый сервис ведёт свои SQL-миграции и журнал версий в своей базе. На этапе 06 заводим по каталогу `services/<service>/migrations` и используем Goose. Миграции применяет отдельный процесс с правами DDL и одной блокировкой на базу. Приложение работает под ролью своего сервиса, а его экземпляры стартуют после успешной миграции. Данные и ограничения описаны в [модели данных](data-model.md).

## Порядок внедрения

| Этап [дорожной карты](../README.md#этапы) | База и изменения | Данные предыдущего этапа |
| --- | --- | --- |
| 06, каркас | Создать три отдельные базы и роли, подключить журнал миграций каждой базы. Проверить доступность `btree_gist` в используемом образе PostgreSQL. | Базы создаются с нуля. |
| 07, фикстуры | Подключить миграции к тестовым контейнерам, подготовить генератор и билдеры для сущностей по мере появления. | Наполнение выполняется отдельно от миграций. |
| 08, аутентификация | `users` — `accounts`, `refresh_tokens`, уникальный индекс email. | Админ создаётся CLI. Учётных записей для переноса пока нет. |
| 09, роли и баны | `users` — `profiles`, `bans`, индексы открытого бана. | Старые аккаунты сохраняют идентификаторы и роли, профили остаются незаполненными. С этого этапа защищённые команды проверяют бан синхронно. |
| 10–11, площадки, залы и игры | На 10-м этапе `games` добавляет `venues`, `halls` и `btree_gist`. На 11-м — `formats` и `games` с проверкой длительности и ограничением пересечений. | Начальные форматы добавляются миграцией справочника. FK на залы и ограничение пересечений действуют с первой записи игры. |
| 12, серии | `games` — `series`, nullable `series_id` и `series_slot_date` с FK и UK, индекс для планировщика. | Прежние игры остаются разовыми. Генератор начинает с запланированных будущих слотов. |
| 13, запись | `games` — `registrations`, счётчик `last_registration_seq`, индексы и проверки отмены. | У существующих игр нет записей, начальный счётчик равен 0. Расписание и время открытия сохраняются. |
| 14, команды | `games` — `team_assignments`, `team_members`, `roster_revision` со стартовым значением 0. | Существующие записи сохраняются. Версии раскладов появятся с первого явного перемешивания каждой игры. |
| 15, outbox и Kafka | Сначала создать топики и мигрировать издателей `users` и `games`, включая `processed_events` в `games`. Затем развернуть запись outbox и консьюмера бана, после них включить публикаторы. | Старые изменения не публикуются задним числом. При включении обработки бана `games` один раз проверяет через `GetAccessState` игроков с неотменёнными записями на предстоящие игры. Действующие баны применяются по тому же правилу, что и события. Прогон можно повторить. До этапа 15 автоматическое снятие через Kafka недоступно. |
| 16, бот | `users` — таблицы привязки, одноразовых токенов и настроек. Бот включается после обновления gRPC в `users` и `games`. | Прежние аккаунты остаются без привязок, настройки по умолчанию действуют до первого изменения. |
| 17, уведомления | `telegram` — `processed_events`, `delivery_jobs` и индексы. Запуск консьюмера, планировщика и отправителя после миграции и готовности gRPC. | Новая группа уведомлений начинает с зафиксированной позиции включения по каждой партиции. Исторические изменения не рассылаются. Напоминания строятся по актуальным предстоящим играм. |
| 18, явка и дисциплина | `games` — `present`, маркер `game.finished` и `auto_ban_requests`. `users` — правило повторной выдачи и ключ `discipline_window_id`. Сначала включаются миграции и API `users`, затем обработка дисциплины и генерация `game.finished`. | Прежние игры и записи сохраняются. Чтобы не наказать игроков за отсутствие недоступных ранее отметок, дисциплина учитывает игры с `starts_at >= attendance_enabled_at`. Момент включения фиксируется один раз для среды. Старые завершённые игры могут получить одно `game.finished` без влияния на дисциплину. |
| 19–21, качество | Redis, метрики и k6 подключаются поверх PostgreSQL. Индексы меняются по измерениям на `load`. | PostgreSQL остаётся источником данных, Redis можно пересоздать. |

Если `late_cancel` добавлен на этапе 13, его факт остаётся в истории. При включении этапа 18 тот же срез `attendance_enabled_at` применяется к фактам дисциплины, включая старые поздние отмены. `discipline_window_id` в `bans` добавляется nullable: исторические ручные баны сохраняют `issued_by`. Длина скользящего окна задаётся согласованно для `games` и `users`. Порог и срок бана использует `games`, выдачу и ограничение повторов контролирует `users`.

## Применение и изменение существующих данных

1. До развертывания прогнать миграции с чистой базы и со схемы предыдущего этапа на копии с представительными данными. Проверить запас места, права, время удержания блокировок и точку восстановления для каждой затронутой базы.
2. Применить миграции до переключения приложения. По умолчанию DDL, изменение данных и отметка версии фиксируются одной транзакцией. Отдельный шаг применяем только там, где команда PostgreSQL требует этого, например при построении индекса `CONCURRENTLY` на большой таблице.
3. Добавлять поля и таблицы совместимо со старым приложением. Если нужен backfill, заполнить поля из фактов владельца детерминированными порциями по PK, сверить число строк, пропуски и дубли. Затем валидировать новые ограничения, переключать чтение и запись, а устаревшие поля удалять отдельным выпуском после вывода старых экземпляров.
4. Перед усилением уникальности или ограничений интервалов вывести конфликтующие ключи для исправления. При обнаружении проблем остановить миграцию до согласованного исправления данных. Справочные форматы добавлять версионной миграцией; данные `dev`, `test` и `load` загружать отдельно.
5. Для межсервисного изменения сперва выкатывать совместимую схему и поддержку чтения, затем записи, работников и издателей. Применение атомарно внутри одной базы; у каждого сервиса своя версия. Совместимость Kafka описана в [каталоге событий](events.md#порядок-и-повторная-обработка).

## Восстановление

| Сбой | Действия |
| --- | --- |
| Транзакционная миграция прервалась | Не включать новую версию сервиса. Проверить журнал версий и причину отказа. После отката PostgreSQL и исправления причины повторить ту же версию миграции. |
| Прерван backfill или нетранзакционная миграция | Сверить состояние и данные с журналом. Возобновить идемпотентный backfill с последней порции. Невалидный индекс после `CREATE INDEX CONCURRENTLY` обнаружить через каталог PostgreSQL, убрать и построить повторно. Включить новую версию после проверки ограничений. |
| Код не стартует после миграции | Вернуть совместимую версию приложения и остановить новые фоновые задачи. Оставить добавленные поля и данные для исправления следующей миграцией. Обратную миграцию применять только до записи новых данных и после проверки её обратимости на копии. |
| Потеря или повреждение данных | Приостановить запись, публикацию и консьюмеров затронутых потоков. Восстановить базу в отдельный экземпляр из резервной копии или PITR, сверить версию схемы, FK, состояние outbox, обработанные события и доставку. При восстановлении нескольких баз выбрать согласованные точки и сверить межсервисные идентификаторы. Сопоставить сохранённые эффекты с Kafka offsets, вернуть потребление к первому неподтверждённому в восстановленной базе событию, воспроизвести повторы и только потом переключить трафик. Если события уже вышли из retention Kafka, сначала восстановить доступный журнал или сверить состояние по сервисам-владельцам. |
| Kafka или Telegram недоступны | Outbox и задания остаются в PostgreSQL. После восстановления возобновить публикацию по исходным `event_id` и доставку сохранённых заданий. Позиция Kafka сама по себе не подтверждает сохранность эффекта после PITR. Повтор внешней отправки при потере результата Bot API может дать дубль. |

При резервировании сохраняются outbox, журнал обработки и ключи доставки вместе с предметными данными. Срок их хранения должен покрывать поддерживаемое окно повтора Kafka и восстановления. Для напоминаний сохраняется ключ задания как минимум до начала игры и завершения возможных повторов доставки. После восстановления критичные сценарии проверяются на тестовых данных из [плана фикстур](fixtures.md).
