# Как вести разработку

Правила для любого изменения в репозитории: ветки, коммиты, pull request, критерии готовности этапа. Список этапов — в [README](README.md#этапы).

## Ветки

Постоянных веток две, остальные — короткоживущие рабочие.

| Ветка | Назначение | Как попадают изменения |
|---|---|---|
| `main` | Стабильные версии (вехи), каждая с тегом `vX.Y.Z` | Только PR из `dev`, merge commit |
| `dev` | Интеграционная ветка, ветка по умолчанию | Только PR из рабочих веток, squash |
| `feature/NN-<slug>` | Этап разработки: новая функциональность | От `dev`, PR в `dev` |
| `docs/NN-<slug>` | Этап проектирования: документы, контракты, ADR | От `dev`, PR в `dev` |
| `chore/NN-<slug>` | Инфраструктура без новой функциональности | От `dev`, PR в `dev` |
| `fix/<slug>` | Исправление ошибки, найденной после merge в `dev` | От `dev`, PR в `dev` |

- `NN` — номер этапа из README, `slug` — пара слов на английском через дефис: `feature/15-registrations`.
- Один этап — одна рабочая ветка и один PR. После merge ветка удаляется автоматически.
- Префикс ветки совпадает с типом основного коммита (`feat`, `docs`, `chore`, `fix`), поэтому по списку PR видно, где проектирование, где код, а где исправления.
- `release/*` и `hotfix/*` не используются: нет продакшена и параллельно поддерживаемых версий.

### Слияние

- **Рабочая ветка → `dev`: squash.** Этап становится одним коммитом, сообщение коммита — заголовок PR. История `dev` читается как список этапов, а подробная история остаётся в PR.
- **`dev` → `main`: merge commit.** Squash здесь нельзя: `main` и `dev` разошлись бы, и каждый следующий PR в `main` показывал бы старые коммиты и конфликты.
- Перед merge рабочая ветка обновляется от `dev` (`git rebase dev`), если в `dev` появились новые коммиты.

### Вехи

Веха — PR `dev` → `main` с заголовком `chore: release vX.Y.Z`. После merge на `main` ставится аннотированный тег:

```sh
git switch main && git pull
git tag -a v0.1.0 -m "v0.1.0" && git push origin v0.1.0
```

Версии — по [SemVer](https://semver.org/lang/ru/). До `v1.0.0` несовместимые изменения повышают минорную версию.

## Коммиты

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/):

```
<type>(<scope>): <description>

[тело]

[футер]
```

**Типы:** `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`, `style`, `revert`.

**Scope** — сервис или область: `users`, `games`, `telegram`, `seed`, `infra`, `api`. Scope необязателен: изменение, которое касается всего репозитория, пишется без него: `docs: add contributing guide`.

**Описание** — на английском, в повелительном наклонении, со строчной буквы, без точки в конце, до 72 символов вместе с типом:

```
feat(games): add soft limit with waitlist
fix(users): reject reused refresh token
test(games): add golden files for 4x4 shuffle
```

**Несовместимые изменения** (например, изменение публичного контракта API) отмечаются `!` после scope и футером:

```
feat(api)!: rename game status field

BREAKING CHANGE: field `state` is renamed to `status` in GET /games
```

Заголовок PR пишется по тем же правилам: после squash он становится коммитом в `dev`, а тело коммита не сохраняется. Поэтому несовместимый этап отмечается `!` в заголовке PR, а футер `BREAKING CHANGE` переносится в описание PR.

## Pull request

- PR открывается в `dev` (вехи — в `main`) и заполняется по шаблону: что сделано, как проверить, что пропущено и почему.
- Заголовок — Conventional Commit, описывающий этап целиком: `feat(games): add recurring games`.
- Один PR — один этап. Найденное по пути, но не относящееся к этапу, уходит в отдельную ветку `fix/<slug>` или в следующий этап.
- Перед merge — самопроверка диффа целиком и отметки в чек-листе шаблона.
- Merge — только при зелёном CI.

## Definition of Done

Этап готов, когда выполнено всё применимое к нему:

- Код и документы этапа в рабочей ветке, история коммитов по Conventional Commits.
- Нетривиальная логика покрыта тестами, `make test` и `make lint` зелёные, CI зелёный.
- Фикстуры обновлены под новые сущности.
- README или `docs/` обновлены: как запустить, что появилось.
- PR в `dev` описан по шаблону.

Этапы проектирования (`docs/NN-*`) заканчиваются документами и PR: тестов, фикстур и `make` в них нет.

## Принцип минимального полного изменения

Ленивый дизайн при полном объёме задачи.

1. **Перед изменением** найти всё, чего оно касается: вызовы, тесты, фикстуры, конфиги, документацию.
2. **Выбирать первый вариант, который решает задачу полностью**, в таком порядке:
   - нужно ли это вообще — неназванные в задаче функции и опции не добавляются;
   - есть ли готовое в репозитории (хелпер, паттерн) — использовать так же, как соседний код;
   - есть ли в стандартной библиотеке Go или уже подключённой зависимости — использовать, новую зависимость ради пары строк не добавлять;
   - иначе — минимальный код, который работает.
3. **Без кода «на будущее»:** абстракций, интерфейсов с одной реализацией, опций и обобщений до второго реального случая. Удалить код лучше, чем добавить.
4. **Объём этапа задаёт его строка в таблице этапов README.** Названные там технологии — требование, а не предмет экономии. Технологии и библиотеки будущих этапов раньше времени не подключаются.
5. **Ошибка исправляется в первопричине, один раз, в общем коде.** Перед правкой находятся все места вызова.
6. **Нетривиальная логика** (ветвление, цикл, парсер, деньги, безопасность) получает тест. Тривиальная правка — нет.
7. **Известное ограничение** помечается комментарием:

   ```go
   // shortcut: users are loaded without pagination, add a cursor when a club exceeds 1000 players
   ```

8. **Не урезается никогда:** валидация на границах доверия, обработка ошибок, ведущих к потере данных, безопасность, доступность, явные требования этапа.

Комментарии в коде объясняют только «почему», которое не видно из кода, одной строкой.

## Защита веток

Настраивается для `main` и `dev` в Settings → Branches (или командами ниже).

| Правило | `dev` | `main` |
|---|:-:|:-:|
| Обязательный PR | ✅ | ✅ |
| Число обязательных approve | 0 | 0 |
| Правила действуют и для администратора | ✅ | ✅ |
| Запрет force push и удаления | ✅ | ✅ |
| Линейная история | ✅ | — |
| Обязательный зелёный CI | с этапа 06 | с этапа 06 |

- Approve не требуется: в репозитории один разработчик, а GitHub не даёт автору одобрить свой PR. Ревью — самопроверка по чек-листу шаблона.
- Линейная история на `dev` запрещает merge commit, поэтому в `dev` попадает только squash. На `main` она выключена, потому что вехи вливаются merge commit.
- Обязательная проверка CI добавляется на этапе 06 вместе с первым workflow: GitHub требует имя существующей проверки.
- GitHub не умеет ограничить исходную ветку PR. Правило «в `main` — только из `dev`» на этапе 06 проверяет отдельный job CI.

Настройки репозитория (Settings → General → Pull Requests): разрешены squash и merge commit, rebase выключен; сообщение squash-коммита — заголовок PR без тела; ветки удаляются после merge. Ветка по умолчанию — `dev`.

Те же настройки через [GitHub CLI](https://cli.github.com/):

```sh
repo=kroissandr/volleybot

gh api -X PATCH "repos/$repo" \
  -f default_branch=dev \
  -F allow_squash_merge=true -F allow_merge_commit=true -F allow_rebase_merge=false \
  -f squash_merge_commit_title=PR_TITLE -f squash_merge_commit_message=BLANK \
  -F delete_branch_on_merge=true

for branch in dev main; do
  linear=false; [ "$branch" = dev ] && linear=true
  gh api -X PUT "repos/$repo/branches/$branch/protection" --input - <<EOF
{
  "required_status_checks": null,
  "enforce_admins": true,
  "required_pull_request_reviews": {"required_approving_review_count": 0},
  "restrictions": null,
  "required_linear_history": $linear,
  "allow_force_pushes": false,
  "allow_deletions": false
}
EOF
done
```
